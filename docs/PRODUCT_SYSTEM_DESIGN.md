# StratPilot：产品、系统与发布设计

更新日期：2026-08-13

## 产品定位

“StratPilot”是一套面向企业经营沙盘的单企业人机协同决策系统。真实使用时，只有我方企业接入决策智能体；其他参赛企业仍由真人控制且其私有操作不可见。系统接收本企业当前状态、已知历史操作、比赛规则、公开订单和规则允许购买的情报，输出可执行的候选经营方案、逐项理由、风险预演和人机差异，最终由用户确认后提交。环境反馈返回后，系统重新规划，而不是假定上一轮预测一定成立。

产品对外名称统一为“StratPilot——企业经营沙盘决策智能体”。`GoAI` 仅保留为现有开发目录和历史仓库标识，不再作为页面、规则通知、PPT 或 Demo 中的产品名称。

## 三个独立系统

系统必须保持以下边界：

| 模块 | 职责 | 是否控制真实对手 | 是否决定财务真值 |
| --- | --- | --- | --- |
| 模拟器与裁判环境 | 生成本场规则和订单，接收所有模拟企业的动作，执行订单冲突、状态转移、报表、违约、破产和排名 | 仅在本地实验中接收对手策略动作 | 是 |
| 我方决策智能体 | 读取我方可见信息，调用资金、资格、产能、履约、订单和风险模块，生成带理由的候选方案 | 否，只服务我方一家企业 | 否 |
| 评估与复盘器 | 比较人工方案与 Agent 方案，记录实际反馈，选择关键节点做反事实分支评估 | 否 | 读取模拟器结果，不修改真值 |

模拟器可以在完全没有我方决策智能体的情况下运行纯用户赛或接受任意策略接口；我方决策智能体也可以通过统一观察/动作协议接入真实比赛适配器，不依赖本地模拟器的内部对象。页面把两者放在同一操作台只是为了 Demo 和实验便利，不代表二者在架构上耦合。

本地比赛中的“模拟对手策略”不是把我们的决策智能体授权给真实参赛者，而是用于生成竞争环境的行为模型：

- 异质经营对手：混合增长、平衡、保守和高风险企业，检验一般鲁棒性。
- 晚期扩张压力对手：部分企业前期争单扩产、后期承受偿债和维护压力，检验风险传导。
- 协同决策对手：模拟对手也使用多模块联合规划但风险档位不同，用于高强度压力测试。
- 保守基线对手：优先现金安全和存续，作为最低难度对照。
- 随机启发式对手：在合法动作中加入随机行为，用于边界、异常和方差测试。

## 每场比赛独立规则

系统不再把某一场省赛规则显示为模拟器唯一规则。内部研究阶段已经从多场企业经营沙盘资料中归纳了产品、市场、认证、融资、厂房、产线、采购、订单、税费、折旧、破产和评分的合理机制及参数范围。创建模拟比赛时，系统依据规则种子在这些范围内生成一份本场独立规则包，并同时生成“比赛规则通知”。

规则通知至少包括：赛程与初始现金、贷款和结算、订单发布与冲突、广告和竞价、研发认证、厂房产线、采购生产、违约破产以及终局评分。通知明确标记为模拟生成规则，不冒充任何赛事官方规则。规则种子、规则包、订单和动作轨迹进入本场审计记录，从而满足同种子可复跑、不同种子可做鲁棒性实验。

规则生成应遵守两级约束：第一级是会计恒等式、阶段顺序、动作合法性和数据类型等不可破坏的硬约束；第二级是在多场比赛观察范围内抽样的成本、利率、税率、研发周期和评分权重。对尚未验证的机制，不应只改变一个数值，而应作为可替换规则模块形成候选规则族。

## 决策输入、输出与对话修订

每个决策节点的输入为：本场规则通知、当前阶段、本企业私有状态、当前时点之前的已知本企业操作、公开订单与公开赛场摘要、合法购买的情报、用户风险偏好和本轮自然语言反馈。默认不输入其他企业私有动作、未来订单归属或历史比赛终局答案。

输出不再只是动作包，而是四层内容：

1. 可读动作清单，例如“借入 100 万，4 季度”“自动线生产 P2 × 1”，页面不展示 JSON。
2. 决策理由，包括负责模块、目标、当前证据、依赖关系、风险模块移除的动作以及预演现金和权益。
3. 反馈审查。用户可以输入“现金压力较大，请减少非必要扩张”等要求；系统先判断是否与规则、可见信息和硬约束相容，再采纳、调整或拒绝。要求查看对手私有信息、保证获单、保证第一或忽略规则的反馈不能被接受。
4. 实际提交后的结果，包括动作接受/拒绝、获单、交付、违约、现金和权益变化、报表以及下一轮复盘建议。

当前反馈解释器是可审计的规则型实现，能调整稳健、平衡和增长档位。后续可以增加 LLM 作为自然语言理解和解释层，但 LLM 不负责财务计算、合法性判断或直接修改状态；所有修改后的动作仍必须经过确定性规则引擎重放。

## 人机差异与反事实准确性

页面当前记录两类即时差异：动作类型一致度和完全相同动作比例。它们只能回答“人工最终方案与 Agent 建议有多像”，不能回答“谁更正确”。例如人工与 Agent 都选择扩产，但产线类型、时点或融资额不同，长期结果可能完全不同；反过来，两份动作不同也可能在不同对手行为下得到相近结果。

真正的决策质量评估必须从同一历史检查点分叉：基准分支执行人工动作，反事实分支执行 Agent 动作；随后使用相同规则、订单种子和可复现对手随机状态重跑整个全局环境。因为一次选单、广告或产能动作会影响竞争者获单和后续现金流，所以不能只重算我方企业，也不能把未来真实动作原样固定后称为严格因果结果。

全量对每个节点、每个候选和多个对手种子重跑确实昂贵。20 个季度的单场确定性模拟本身不算大，但节点数 × 候选数 × 对手组合 × 规则种子会快速增长。因此采用三级评估：

1. 在线轻量评估：合法性、现金/权益预演、动作一致度、短期履约缺口，必须实时完成。
2. 终局抽样反事实：只选择高影响节点，例如首次融资、首次扩产、大额竞单、现金安全垫突变和违约前一季；每个节点运行少量共同随机数分支。
3. 离线批量评估：针对规则种子、订单种子和对手组合并行运行，报告 Agent 相对人工的终局得分增量、破产率差、交付率差、最差分位数和置信区间。

建议把“反事实优势率”定义为在同一检查点和同一随机场景集合中，Agent 分支终局效用高于人工分支的场景比例，同时单独报告平均增益和最差分位数。该指标仍是模拟环境中的估计，不应表述为真实比赛的绝对准确率。为实现严格复跑，检查点除所有企业状态外，还要保存订单分配日志、当前阶段、策略内部状态和随机数状态；仅复制我方现金和库存是不够的。

## “三种子校准”的正确解释

历史文档中的“三种子校准”指在同一套内部基准规则和同一对手总体配置下，更换三个订单随机种子，完整运行三场比赛后取指标均值。它用于确认结果不是偶然依赖单一订单样本，并比较模拟指标与内部历史基准的数量级，不代表系统只支持三场比赛，也不代表所有比赛使用同一规则。

新版评估应把规则种子、订单种子和对手组合分开：每场模拟赛先生成自己的规则通知，再在该规则下生成订单和对手；跨场汇总时报告范围、均值、方差和最差分位数。原始比赛规则和企业数据只作为内部规则范围提取、状态机验证和聚合校准依据，不进入公开演示仓库。

## Demo、脱敏与公开发布

Demo 使用系统生成的规则、订单和企业数据，本身不需要对不存在的真实身份做“事后脱敏”；但应从源头使用明显虚构且不可回溯的名称，例如“青屿制造”“远岚科技”或“模拟企业 01”，不要使用真实学校、队伍、账号、赛场编号和真实企业昵称。视频不显示内部规则参数全集、随机种子、令牌、完整导出、真实数据路径或历史企业映射。

项目应维护两个仓库：

- 内部开发仓库：保存真实/授权研究数据、规则提取证据、完整源码、实验轨迹和校准工具，不公开。
- 脱敏发布仓库：只保存作品简介、PDF、Demo 视频、聚合指标、虚构样例和必要的运行说明。若初赛不要求源码，可以只提供一个面向目标系统编译/打包的可运行文件及校验值，不提供完整 Python 源码、规则范围、Agent 阈值和真实数据。

“只放编译后的文件”能提高复现门槛，但不是可靠保密措施：可执行文件仍可被逆向，且必须包含第三方许可证、运行平台、依赖、校验值和恶意软件误报说明。更可靠的边界是只发布模拟数据、限制导出、移除真实资料、减少内部参数暴露，并保留服务端核心模块。公开仓库建立前必须对 Git 历史而不只是当前目录执行敏感信息扫描。

## 后续实现顺序

1. 冻结模拟器—决策智能体—评估器的进程级接口，允许三者独立启动和替换。
2. 为每个阶段保存完整可恢复检查点和策略随机状态，实现高影响节点的终局反事实抽样。
3. 把决策解释从模块级理由细化为每个动作的目标、证据、依赖、预期收益和主要风险。
4. 增加多轮反馈协议：原建议 → 用户反馈 → 合理性判断 → 修订建议 → 人工确认，并将每次修订保存为不可覆盖的审计链。
5. 用多规则种子、多订单种子和多对手组合评估鲁棒性，替代只报告三个固定订单种子的表述。
6. 最终创建脱敏发布仓库，生成虚构演示赛、可运行发布物、SHA-256 校验值和第三方许可证清单；真实规则提取数据和内部实验轨迹不上传。
