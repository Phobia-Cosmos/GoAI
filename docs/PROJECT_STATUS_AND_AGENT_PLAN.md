# GoAI 项目现状、目标与 Agent 实施路线图

更新时间：2026-08-07 14:44

## 1. 最终目标

GoAI 的最终目标是构建一个面向企业经营比赛的辅助决策系统：当用户只提供一场比赛的部分规则、企业状态、订单和历史经营记录时，系统能够先判断数据和规则的可信程度，再重建当前企业状态，生成若干合法经营方案，使用确定性沙盘预测这些方案对现金、库存、产能、订单、贷款、报表和最终评分的影响，最后把可解释的比较结果交给人确认。

最终系统首先是“辅助人决策”的系统，不是直接替人提交动作的全自动系统。系统必须能够回答：当前处于什么状态；哪些动作可以做；每个动作的前置条件是什么；选择某个订单、投放广告、贷款、研发或生产后未来几个季度会发生什么；方案的收益、风险和不确定性是什么；如果改变决策，最终结果会如何变化。

系统的基本闭环是：

```text
比赛资料/平台记录/人工输入
        ↓
数据清洗、来源标记、比赛与规则绑定
        ↓
当前状态重建与规则完整性检查
        ↓
生成候选动作和多季度候选方案
        ↓
确定性规则校验与沙盘分支重放
        ↓
现金、权益、履约、产能、评分和风险比较
        ↓
给出推荐、备选、解释和不确定性
        ↓
人工确认后提交动作
        ↓
记录真实结果，进行偏差分析和后续校准
```

## 2. 当前工作为什么要做

此前看起来像是在整理很多 Excel、实现 VPD、重放比赛和随机生成数据，实际上这些工作分别对应最终 Agent 的必要基础设施：

| 已完成的工作 | 对最终 Agent 的作用 |
| --- | --- |
| 原始 XLS/XLSX/DOCX 解析 | 让系统能够接收不同比赛的真实资料，而不是依赖手工录入 |
| 标准化 CSV/SQLite/JSONL | 让不同比赛的数据可以使用统一字段进入算法和状态机 |
| 来源、比赛 ID、规则版本和 provenance 标记 | 防止把不同场次混在一起，或把模拟结果当成历史事实 |
| XA 规则转换和冻结 | 提供一套相对完整的正式规则基准，用于首先验证状态机和 Agent 接口 |
| 14 场比赛的推断规则包 | 让系统具备跨比赛的兼容接口，但不宣称这些推断规则是正式裁判规则 |
| 历史事件重放与硬约束检查 | 验证事件、现金余额、订单和报表结构是否可以被程序解释 |
| 完整财务状态机 | 将贷款、采购、生产、交付、应收、折旧、税费和违约变成可计算的状态转移 |
| 比赛式 XLSX 导出与回读 | 验证模拟结果能否以接近真实比赛的文件形式交换和再次处理 |
| 模块化指标和策略比较 | 让 VPD/OE、现金安全、履约、偿债等指标可以替换和消融比较 |
| 多企业沙盘接口 | 为未来多个 Agent 竞争、对手情景和反事实重放预留环境 |

因此，当前阶段的核心产物不是一个已经能自动经营的 Agent，而是一个可以承载 Agent、验证 Agent、追踪 Agent 决策的确定性底座。

### 3.3 数据可信等级

所有进入 Agent 的数据都必须保留以下等级：

| 等级 | 含义 | 可用于什么 |
| --- | --- | --- |
| `observed` | 源文件或平台直接记录 | 历史回放、特征提取和事实核对 |
| `derived` | 按已声明公式确定性计算 | 报表指标、订单成本、现金连续性 |
| `inferred` | 根据多个结果推断，但存在替代解释 | 候选规则、实验性重放，不可直接称正式规则 |
| `simulated` | 随机生成或按传统沙盘补齐 | 压力测试、接口测试、策略对抗 |
| `missing` | 当前没有证据 | 必须提示用户补充，不能自动编造 |

只有规则绑定已确认且输入数据为 `observed + derived` 的部分，才可以作为正式历史回放基准。`inferred` 和 `simulated` 只能用于候选仿真和系统验证。

## 4. 截至目前已经完成的系统能力

### 4.1 数据处理和规则层

已经完成：

- XLS/XLSX、DOCX、Markdown 和现金流文件的解析。
- 统一的企业、订单、现金流、事件、报表、规则和来源字段。
- SQLite、CSV、JSONL 和数据字典输出。
- `rule_packs`、融资条款、规则缺口、动作定义、动作别名和结构化事件表。
- XA 正式规则转换链路，并保存源文件、规则版本和证据。
- 14 场比赛的 `rules_inferred_v2.json` 和运行时推断报告。
- `observed / inferred / simulated` 来源隔离，避免数据污染。

当前不足是：除 XA 外，多数比赛缺少可以证明完整规则的正式规则手册、完整未分配订单池和全局结算说明。因此这些比赛可以做结构化分析和候选仿真，但不能声明已经恢复了正式裁判逻辑。

### 4.2 历史回放和硬约束

`match_replay.py`、`run_all_match_replays.py` 和 `hard_constraints.py` 已经支持：

- 14 场比赛逐场规则包加载。
- 事件按季度和企业排序重放。
- 现金流水连续性检查。
- 订单 ID、企业归属、数量、价格和订单时间检查。
- 三张报表的资产、负债和权益恒等式检查。
- 传统选单/竞单策略作为可替换服务层。
- 历史事件、季度日志、订单分配、最终结果和验证报告输出。

历史回放汇总表明 14 场的硬约束和现金恒等式通过，但旧回放仍明确标记为 `partial_accounting`，因为部分场次的税费、折旧、应收、报表结算和全局订单规则不是原始数据中可以唯一确认的事实。

### 4.3 完整候选财务沙盘

`src/goai_data/full_sandbox.py` 已经实现一个可配置的候选状态机，覆盖：

- 企业初始现金、权益、库存、市场、产品和 ISO 资格。
- 厂房购买、租赁、出售和折旧。
- 手工线、自动线、柔性线和租赁线的建设、转产、维护和折旧。
- 原料常规采购、到货、紧急采购和 BOM 消耗。
- 产品、市场和 ISO 研发进度及分期结算。
- 生产、在制品、产成品和订单交付。
- 现金订单、应收账款、应收贴现和到期回款。
- 短贷、长贷、利息和本金结算。
- 订单违约、违约金、管理费、维护费、租金、税费和年度三张报表。
- 破产检查、最终排名和资产负债平衡。

该状态机是“可运行的传统候选规则”，不是 XA 隐藏规则的官方证明。它的价值是让 Agent 有一个白盒、可回放、可替换的前向环境。

### 4.5 指标和决策内核

`decision_system.py` 已提供模块化指标和策略接口，当前指标包括：

- 现金安全。
- 偿债能力。
- 权益/利润增长。
- 订单履约率。
- 产能利用率。
- 最终得分代理。

当前同时保留安全、平衡和增长三类权重配置，并支持指标消融实验。VPD/OE、PSS、EPSS、商分和生命周期分析可以作为额外 `DecisionMetric` 接入，但不应直接拥有状态修改权限。

### 4.6 当前 Agent 能力

当前已有的 Agent 能力是确定性 MVP：

- 读取规则状态和企业快照。
- 列出候选动作。
- 检查动作名称、参数和即时现金安全。
- 对候选方案进行状态转移和指标排序。
- 在多企业环境中使用可替换的策略对象。
- 记录动作、奖励、事件、状态和结果。

当前还不是最终 Agent，原因是：

- 还没有对所有比赛完成正式规则绑定。
- 还没有稳定的“部分数据输入后状态补全”流程。
- 还没有把真实公共订单、公开报表和信息时点完整接入观察空间。
- 还没有经过跨比赛、跨种子、跨对手组合的策略泛化验证。
- 还没有人工确认、提交适配器和真实结果回流闭环。
- LLM 尚未接入；即使接入，也只能作为规划、解释和工具编排层。

## 5. 最终 Agent 的建议架构

最终系统建议采用“确定性内核 + 可替换决策策略 + 可选 LLM”的结构，而不是让 LLM 直接计算财务结果。

```text
数据导入器
    ↓
比赛/规则绑定器
    ↓
状态重建器 + 信息可见性管理
    ↓
确定性报表状态机（唯一真值来源）
    ├── 审计与硬约束
    ├── VPD/OE、PSS/EPSS、商分等指标
    └── 多季度沙盘分支
            ↓
候选动作生成器 / 搜索器 / BC策略 / LLM规划器
            ↓
候选校验、评分、风险和反事实比较
            ↓
人工确认界面
            ↓
标准事件提交与结果回流
```

### 5.1 四个核心服务

| 服务 | 作用 | 是否允许修改状态 |
| --- | --- | --- |
| 数据与规则服务 | 导入资料、绑定比赛、提供规则和缺口 | 否 |
| 报表状态服务 | 重放事件、自动结算、生成状态和三张报表 | 是，唯一真值来源 |
| 指标诊断服务 | 计算 VPD/OE、PSS/EPSS、现金安全、履约、风险和评分代理 | 否 |
| 决策编排服务 | 生成方案、调用沙盘、比较候选并请求人工确认 | 只能提交经过校验的事件草稿 |

### 5.2 一个季度的决策流程

1. 读取当前 `GameState`、本季度 `InformationSet`、已确认 `RulePack` 和用户目标。
2. 检查状态是否完整；如果只得到部分数据，输出缺失字段和置信度，不隐藏假设。
3. 生成候选动作，例如生产排产、订单选择/竞单、广告、研发、采购、融资和贴现。
4. 先执行硬约束检查，再在沙盘分支中向前模拟 1 季、4 季和剩余比赛周期。
5. 计算最低现金、破产概率/次数、权益变化、利润、履约率、产能利用率、订单机会成本和最终评分代理。
6. 形成推荐方案、保守方案和增长方案，说明每个方案的前置条件、风险和不可确定部分。
7. 由人确认或修改动作，系统将确认结果转换为标准事件。
8. 记录 `DecisionCycle`、人工修改、提交结果和下一季度的真实状态，供后续评估。

### 5.3 LLM 的合理位置

LLM 可以用于：

- 从题面和人工描述中提取规则草稿。
- 将自然语言意图转换为候选动作 JSON。
- 解释不同方案为什么不同。
- 根据检索到的历史案例生成可读报告。
- 在候选失败时解释约束冲突并提出修正方向。

LLM 不应直接负责：

- 计算现金、库存、贷款、税费和报表。
- 判定动作是否合法。
- 绕过订单资格、产能、交期和破产约束。
- 直接写入在线状态或提交比赛动作。

是否使用 LLM 不是系统能否运行的前置条件。基础 Agent 可以先使用规则策略、候选搜索、模仿学习或离线策略；等状态机和数据契约稳定后，再接入开源大模型进行规划和解释微调。

## 6. 后续必须补充的数据

如果目标是“提供一场比赛的部分数据后辅助决策”，每场比赛至少需要以下数据集合：

| 数据集合 | 最低字段 |
| --- | --- |
| 比赛元信息 | `match_id`、企业数、起止时间、规则版本、数据来源 |
| 正式规则 | 初始资本、管理费、贷款、税费、折旧、研发、市场、ISO、厂房、产线、订单、评分和破产规则 |
| 企业初始状态 | 现金、权益、库存、贷款、市场/产品/ISO 资格、厂房、产线、在途事项 |
| 企业事件流 | 事件 ID、时间、企业、动作、参数、现金影响、来源和是否系统自动结算 |
| 全局订单池 | 订单 ID、发布日期、市场、产品、ISO、数量、价格、交期、账期、订单类型、分配结果 |
| 企业订单表 | 企业获得的订单、报价/广告优先级、交付、违约和回款状态 |
| 公开信息 | 年度报表、公开排名、破产信息、订单公开时点和可见主体 |
| 三张报表 | 每年或每季度的资产负债表、利润表、现金流量表及来源字段 |
| 结果标签 | 最终权益、最终排名、破产季度、综合评分和官方结果 |

如果缺少全局订单池，系统可以辅助生产、融资和库存决策，但不应声称能够准确预测选单/竞单结果。如果缺少正式规则，系统可以生成候选规则仿真，但必须在界面上显示“不确定规则”。

## 7. 分阶段实施计划

### 阶段 P0：数据和规则清理

目标是建立每场比赛的最小可用资料包，而不是继续增加模型复杂度。

需要完成：

- 每场比赛建立 `DatasetManifest` 和 `RuleBinding`。
- 明确文件属于全局规则、企业初始状态、事件流、企业订单还是结果数据。
- 将正式、推断、继承和模拟规则分开保存。
- 为每个缺失字段记录原因、影响范围和可替代假设。

验收标准：给定任意一个比赛目录，系统能明确回答“有哪些数据、哪些规则、哪些缺失、哪些可以回放、哪些只能模拟”。

### 阶段 P1：统一状态和报表真值

需要完成：

- 报表 Agent 和当前 `FullFinancialDynamics` 使用同一套 `RulePack`、`GameState`、`NormalizedEvent` 和 `Reports` 协议。
- 建立初始状态校验、事件幂等、状态 ID、版本 ID 和审计日志。
- 用 XA 做逐季度回放，对现金、库存、贷款、产线、订单和三张报表逐项对账。
- 对旧比赛只启用被证据支持的字段，其余显式保持 missing/inferred。

验收标准：同一事件流只能得到一个确定性状态；重复回放结果一致；状态机、报表 Agent 和导入回读的关键余额一致。

### 阶段 P2：单企业辅助决策 MVP

需要完成：

- 输入当前企业状态、公共信息和用户目标。
- 生成保守、平衡、增长三类候选方案。
- 每个候选都在独立沙盘分支中仿真。
- 输出候选动作、前置条件、结果区间、风险和解释。
- 支持用户修改方案并重新仿真。

验收标准：对一个已确认规则的比赛，系统可以在每个季度给出至少三套合法候选方案，所有方案都可回放，且没有违反硬约束的动作进入人工确认列表。

### 阶段 P3：指标和 Agent 比较

需要完成：

- 将 VPD/OE、PSS/EPSS、现金安全、偿债、履约、产能和最终评分代理统一注册为指标插件。
- 对指标进行权重、消融和目标偏好实验。
- 记录不同策略、不同订单种子和不同对手组合的结果。
- 使用历史企业做按比赛留出验证，不能随机把同一场的相邻季度同时放入训练和测试。

验收标准：明确某个指标对推荐方案、破产率、履约率和最终评分的实际影响，并能说明在哪些比赛类型上不稳定。

### 阶段 P4：部分数据输入和不确定性决策

需要完成：

- 数据完整性诊断器。
- 基于已知字段的状态补全，但补全结果带置信度和候选范围。
- 多个规则假设并行仿真，而不是选择一个假设伪装成事实。
- 输出“在所有可行规则假设下都成立”的稳健建议。

验收标准：当缺少全局订单或税费规则时，系统不会给出虚假的精确排名，而是给出可执行建议、假设列表和结果区间。

### 阶段 P5：LLM 和多 Agent 沙盘

需要完成：

- 先用确定性策略和历史行为策略作为对手。
- 再接入 LLM 规划器，但强制输出结构化动作草稿。
- 由规则状态机统一校验、执行和结算。
- 支持人工 Agent、规则 Agent、搜索 Agent、LLM Agent 混合比赛。
- 运行多种初始订单、企业数量、规则假设和随机种子。

验收标准：LLM Agent 不得降低硬约束通过率；在固定预算下，至少不劣于确定性基线；所有建议可解释、可回放、可审计。

## 8. Agent 验证方案

Agent 是否“真正有用”不能只看最终分数，需要同时检查：

| 验证维度 | 指标 |
| --- | --- |
| 合法性 | 非法动作率、硬约束违反率、状态机拒绝率 |
| 财务安全 | 破产率、最低现金分位数、现金最大回撤、偿债覆盖 |
| 经营结果 | 期末权益、利润、最终评分代理、订单履约率 |
| 运营质量 | 产能利用率、库存周转、在途订单、交付延期 |
| 稳健性 | 不同种子、订单池、对手组合和规则假设下的均值与方差 |
| 泛化能力 | 按比赛留出、按企业留出、未见订单组合测试 |
| 可解释性 | 推荐理由与真实状态字段的对应率、人工采纳率 |
| 工程可靠性 | 重放一致性、报表平衡、事件幂等、审计完整性 |

必须设置的基线包括：保持现金策略、规则启发式策略、历史行为模仿策略、随机合法策略和人工方案。Agent 只有在安全性不下降的前提下提高权益或履约，才算有实际价值。

## 9. 当前不应做的事情

- 不要在正式规则和状态机未稳定前微调 LLM 并把模拟事件当标签。
- 不要把 VPD/OE 单独当作最终目标；它只是一个可插拔诊断指标。
- 不要把一场比赛的拟合权重直接宣称为所有比赛通用规律。
- 不要用缺失的全局订单池训练选单和竞单 Agent。
- 不要让 LLM 直接修改现金、库存、报表或比赛状态。
- 不要把旧比赛的 `rules_inferred_v2.json` 改名为正式规则。
- 不要只通过最终排名评价 Agent，必须检查过程中是否破产、违约或违反规则。

## 10. 当前结论

截至 2026-08-07，GoAI 已经从“数据和指标原型”发展为“具备规则包、事件重放、财务状态机、多企业环境、模块化指标和模拟数据生成能力的 Agent 底座”。系统已经可以生成候选动作并在模拟环境中比较后果，但还没有达到可以在真实比赛中自动替代人做决策的程度。

当前最重要的工作不是继续增加 LLM 能力，而是完成一场真实比赛的高质量数据闭环：明确规则、初始状态、全局订单、事件时间、公开信息和报表结算。完成这个闭环后，单企业辅助决策 Agent 才能被可靠验证；在此基础上，再扩展到多 Agent 对抗和 LLM 规划。

下一步优先级应为：

1. 选定一场数据最完整的比赛，完成统一 RulePack 和逐季度状态对账。
2. 建立单企业季度决策 API 和三套可解释候选策略。
3. 将 VPD/OE、现金安全、履约和评分代理接入统一指标服务并开展消融实验。
4. 使用历史留出和多个模拟种子验证 Agent 的安全性和泛化。
5. 最后接入 LLM，作为结构化规划和解释层，并保留人工确认。
